# datasheet PDF 内容处理策略

> 这份文档把「表格怎么办 / 图怎么办 / 检索方式选哪个」三件事合成一套完整方案。
> 所有数字都是在你自己的 PDF 上实测出来的，不是从教程里抄的。

---

## 0. 一句话总纲

**一份 PDF 里有三类内容，各有各的处理法，但最后统一成同一种「块」进入 RAG。**

那个统一的「块」只有两个核心字段：

| 字段 | 给谁用 | 要求 |
|---|---|---|
| `index_text` | 送 embedding 建向量库 | 短、密、容易被检索命中 |
| `content` | 命中后喂给 LLM | 全、准、**数值一个字都不能改** |

这一个拆分同时解决了三件事：摘要索引、表格数值不丢、图片只做定位。

## 1. 先做一次体检：你的 PDF 属于哪一类

**这一步决定后面所有技术选型，必须先做。**

| PDF 类型 | 判据 | 处理策略 |
|---|---|---|
| 电子原生（**你是这种**） | `get_text()` 有内容 | 直接读文本层 + 读矢量图元 |
| 扫描件 | `get_text()` 为空 且 整页一张大位图 | **这才需要 OCR** |

实测结论（沁恒 CH32F103，29 页）：

```
需要 OCR 的页数：0
矢量框图页：p3 / p4 / p5 / p21 / p24 / p27
```

⚠️ 判据要写全，只看「矩形多」会把表格误判成图：

```python
likely_diagram = rects >= 10 and lines >= 50   # 两个条件必须同时成立
```

p12~p19 有 700~900 个矩形但连线不到 5 条 —— 那是**表格**，不是图。

## 2. 三类内容各自怎么处理

| 内容 | 判据 | 处理方式 | 状态 |
|---|---|---|---|
| 正文段落 | 有文字 | 按小节标题切块 | ✅ 已做好 |
| 表格 | `find_tables()` 抽出 | 结构化序列化，**绝不 LLM 摘要** | ⚠️ 有缺陷 |
| 矢量框图 | `rects>=10 and lines>=50` | 读坐标还原层级 | ✅ PoC 已跑通 |
| 扫描位图 | 文本层为空 | OCR | ⛔ 你一份都没有 |

## 3. 表格：判据是字符数，不是行数

### 3.1 你的真实数据（263 张表）

| 数据行数 | 张数 | 占比 |
|---|---|---|
| ≤3 行 | 77 | 29% |
| 4~5 行 | 63 | 24% |
| 6~10 行 | 67 | 25% |
| 11~20 行 | 35 | 13% |
| 21~50 行 | 21 | 8% |
| >50 行 | **0** | **0%** |

**中位 5 行，最大仅 42 行。** 字符数 min / 中位 / max = **59 / 571 / 16008**（落差 270 倍）。

### 3.2 所以业界那两条规则对你不适用

| 业界规则 | 出处 | 为什么不适用 |
|---|---|---|
| 大表按 5~20 行一组 | AI/TLDR | 你 79% 的表不到 10 行，覆盖不到 |
| 小表（<10 行）整表一块 | Logic Loop Tech | 只看行数会掉进下面的陷阱 |

**陷阱区实测：26 张表（10%）行数 ≤10 但字符 >1500**，行数规则必然漏掉它们。

### 3.3 决定性反例

`ATmega328P_Datasheet/page_193`：

```
总行数 9 行     整表 16008 字符
内容：| Reception of the own slave address and one or S SLA W A DATA A DATA A P or S ...
```

**这不是表，是 I2C/TWI 时序图被误判成表格。** 而且它躲过了 `p0_2_filter_tables.py` 的过滤
（那份剔了 180/363，剔的理由集中在「表头占位名占比过高」「解析后没有数据行」，这张溜过去了）。

照「行数<10 就整表一块」执行，会产出 16008 字符的巨块 → embedding 被彻底稀释。

### 3.4 正确的执行顺序

> **先滤伪表 → 再按字符数切。行数只当「是否值得保留」的辅助信号。**

顺序搞反了，你是在给垃圾做精细分块。

```python
SMALL_TABLE_CHARS = 1500   # ≤ 这个数 -> 整表一块
GROUP_MAX_CHARS   = 1500   # 分组时每组上限
MIN_DATA_ROWS     = 2      # 少于 2 行数据行 -> 疑似伪表，先过滤
```

只有 **181 张（69%）** 落在 `行数≤10 且字符≤1500` 的安全区，适合整表一块。

### 3.5 组大小怎么定：看行间关系，不看行数

| 表 | 形态 | 行间关系 | 怎么切 |
|---|---|---|---|
| p281/282/283 指令集 | 42 行 6 列 | **每行一条独立指令** | **每行一块**，不是 5~20 行一组 |
| p277/278 寄存器位 | 38 行 11 列 | **每行一个独立寄存器** | **每行一块** |
| 型号对照表 | 行=型号，列=资源 | 需要横向比较 | 整表一块（若 ≤1500 字符） |

关键点：**「每行独立」的表，捆成组反而有害** —— 问一条指令时要多看 19 条无关指令。

### 3.6 表格序列化格式

```python
# 正确：每行都重复表头，用「列名: 值」而不是 markdown 竖线
[表格] 表1-1 产品资源分配；列：产品型号、资源差异、CH32F103C6T6、CH32F103C8T6
产品型号: 芯片引脚数；资源差异: 48；CH32F103C6T6: 48
```

三条铁律：
1. **绝不做 LLM 摘要** —— 一旦把 `2.0 to 3.6 V` 写成「约 2 到 3.6 伏」，评测题永久失败
2. **每行必须重复表头** —— 否则「值」不知道属于哪一列
3. 用 `列名: 值` 而不是 markdown 竖线 —— embedding 对前者更敏感

### 3.7 中文表格两个已知缺陷（CH32F103 入库前要修）

| 缺陷 | 表现 | 后果 | 修法 |
|---|---|---|---|
| 汉字间插空格 | `定 时 器` | 检索「定时器」永远匹配不上 | 正则去掉汉字间的空格 |
| 子行丢父表头 | `通用 2 3 3 3` | 模型不知道在说什么 | 纵向合并单元格继承，拼成 `定时器-通用` |
| 斜线表头 | `产品型号 / 资源差异` | 谁管行谁管列看不出 | **认了，别硬修** |

## 4. 矢量框图：读坐标，不用 OCR

### 4.1 为什么不用 OCR

你的框图**不是位图**，是矢量工程图：

```
get_drawings() 实测：59 个矩形 / 542 条直线 / 71 条曲线 / 80 个小位图碎片
```

用 OCR 等于**把精确坐标烧成像素，再让模型从像素里猜回来** —— 主动降级。

### 4.2 已实现：`backend/figure_extract.py`

新增的独立文件，**没有 import、也没有改动你任何现有代码**。

```powershell
# 扫描整份 PDF，列出哪些页是矢量框图
.venv\Scripts\python backend\figure_extract.py --pdf datasheets/CH32F103_Datasheet_CN.pdf --scan

# 还原指定页的结构
.venv\Scripts\python backend\figure_extract.py --pdf datasheets/CH32F103_Datasheet_CN.pdf --page 3
```

实测产出（第 3 页系统框图，**51 个带名模块框**）：

```
ARM Cortex-M3
  ├ SWD    ├ TPIU    └ NVIC
SYSCLK AHBCLK APB1CLK APB2CLK RTC_CLK IWDG_CLK
  ├ PLL   ├ 4~16MHz Crystal   ├ 32.768kHz Crystal
  ├ 8MHz RC OSC   ├ 40kHz RC OSC   └ MUX & DIV

第 1 列（18 个）：GPIOA~D、TIM1、SPI1、USART1、ADC、TouchKey、VREF、Temp Sensor…
第 4 列（22 个）：RTC/BKP、IWDG/WWDG、TIM2~4、USART2~3、SPI2、I2C1~2、bxCAN、DAC…
```

列分组结果与真实的 APB2 / APB1 划分完全吻合。

### 4.3 写代码时踩到的两个坑

这两个坑是这个模块的真实经验，换任何 PDF 都会遇到：

1. **父框取标签必须排除子框覆盖的文字**（按词中心点判定），
   否则 `ARM Cortex-M3` 的标签会变成 `ARM Cortex-M3 TPIU NVIC SWD`
2. **层级只保留直接子**（A⊃B⊃C 时 A 的子里不能有 C），
   否则同一个 `TPIU` 会在树里出现两次

### 4.4 还没解决的部分

**542 条连线的「谁连谁」没做。** 现在的总线归属是靠 x 坐标聚类**间接推断**的。

要真正做拓扑，得分析 `get_drawings()` 里每条 `"l"` / `"c"` 的**首尾端点落在哪个框内**。
这是下一步，别以为已经完事了。

### 4.5 双通道：几何结构为主，渲染图为辅

| | 主体 | 补充 |
|---|---|---|
| 载体 | 结构化文本（上面的样子） | 该页渲染的 PNG |
| 给谁 | DeepSeek 文本模型 | **`deepseek-v4-flash-vision-exp`** |
| 何时用 | 每次命中都给 | 只在问图内细节时 |

DeepSeek 视觉模型情报（2026-08-21 上线）：

- **一张图封顶 384 token**（自动缩到约 800×800）
- 费率同普通 Flash：**输入 1 元 / 百万 token** → 一次带图问答约 **¥0.005**
- 三条硬限制：**图只能放 user message** / **必须是那个 vision 模型名**（其他返回 400）/ base64 单图 ≤32 MB

> 为什么把结构化文本也塞进去：**只给图，模型会开始猜**；
> 先给准确文本再让它「看着图补充」，幻觉率会低一个量级。

## 5. 检索方式：不是选一种，是按问题类型分流

| 问题类型 | 例子 | 靠什么赢 |
|---|---|---|
| 型号 / 数字精确匹配 | 「C8T6 有几个通用定时器」 | **BM25**（向量对型号串不敏感） |
| 语义 / 概念 | 「支持哪些低功耗模式」 | dense 向量 |
| 表格里的值 | 「C8T6 的 Flash 多大」 | 混合召回 + 表头回填后的结构化块 |
| 框图 | 「有系统架构图吗」 | 图块指针 + 几何结构 |

**推荐起步：先做混合检索（BM25 + dense + RRF），零 token 开销、当天出数据。**

| 维度 | 混合检索 | 摘要索引 |
|---|---|---|
| 属于哪层 | 召回层（怎么找） | 索引层（什么被向量化） |
| 治什么病 | **漏召**：型号、数字找不到 | **语义稀释**：块太大向量被平均 |
| 成本 | **零**（BM25 是本地统计） | 1687 次 LLM 调用，约 ¥1~3 |
| 你的情况 | 供电电压答成 −0.3~4.0V 是精度问题，**RRF 能治** | 治不了上面那个 bug |

两者正交，可叠加，但**先做混合检索** —— 它还顺便提供了要ogene对照基线。

## 6. 执行顺序 Checklist

| # | 做什么 | 验收标准 | 状态 |
|---|---|---|---|
| 1 | **跑 20 条评测集基线** | 拿到「大改前」的真实数字 | ⬜ |
| 2 | 上加混合检索 + RRF | 再跑一次评测集，对比 | ⬜ |
| 3 | 补 `p0_2` 伪表判据（单行超长） | 收掉 page_193 那类 | ⬜ |

| 5 | 表格块改结构化序列化 | 每行「列名: 值」 | ⬜ |

**必须先做第 1 步。** 没有基线数据，后面每一步你都无法证明它有没有用。
